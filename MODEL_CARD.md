#### Description

YOLOX is the anchor-free YOLO variant of "YOLOX: Exceeding YOLO Series in 2021" (Ge, Liu, Wang, Li and Sun, arXiv:2107.08430; Megvii Inc.), and this pipeline packages the **YOLOX-S** checkpoint `yolox_s.pth` (72,089,125 bytes) from the upstream GitHub release `0.1.1rc0`. YOLOX publishes no Hugging Face model repository, so the pinned identity here is a release **tag** plus a SHA-256, not a Hub revision: `f55ded7181e1b0c13285c56e7790b8f0e8f8db590fe4edb37f0b7f345c913a30`, recorded in `weights/yolox-s/dimer-base-manifest.json` and re-checked before the file is opened. The architecture is a CSPDarknet backbone and a PAFPN neck at YOLOX-S scale (`depth = 0.33`, `width = 0.50`, from upstream `exps/default/yolox_s.py`) feeding a **decoupled head** with separate classification, regression and objectness branches at strides 8/16/32; over a 640×640 letterboxed image that is 80² + 40² + 20² = 8400 anchor points, each emitting one box, one objectness logit and one logit per class. There are no anchor boxes and no softmax over classes: objectness and class probability are independent sigmoids whose product is the score, and per-class NMS selects the survivors. The constructed model holds 8,968,255 parameters, consistent with the upstream README's 9.0 M. At training time the same head performs **SimOTA** label assignment — an IoU-and-classification cost between each ground-truth object and each candidate anchor, solved for a dynamic number of positives per object — which is what makes a short fine-tune viable. Because the upstream `yolox` distribution cannot be installed into a pinned runtime (its `install_requires` pins `onnx==1.8.1`, `onnxruntime==1.8.0` and `onnx-simplifier==0.3.5` beside a bare `torch>=1.7`, and `--no-deps` still fails because `yolox.models.yolo_head` imports `yolox.utils`, whose `__init__` needs `cv2`, `loguru` and `thop`), the eight model modules this pipeline runs are **vendored** from upstream commit `419778480ab6ec0590e5d3831b3afb3b46ab2aa3` (tag `0.3.0`, whose own `build.py` points its download URLs back at the `0.1.1rc0` assets) with three declared edits, recorded file-by-file with digests in `docs/UPSTREAM.md` and re-checkable with `tools/vendor_upstream.py --check`. What this repository adds is packaging and two capabilities: `verify_snapshot` and `stage_missing_files` (manifest digest checking and release-asset staging), `YoloxDetectionPipeline.from_pretrained` (verified local loading, `torch.load(weights_only=True)` only after the digest check, and optional re-heading onto a caller's class vocabulary with a seeded initialisation), `detect` (input validation, caller-owned confidence and NMS thresholds, sorted pixel-space output), `finetune` (a bounded SimOTA fine-tune calling upstream's own loss, with the backbone frozen by default), `evaluate` and `average_precision` (COCO-style AP@[.50:.95] and AP50 over a held-out set), `save_artifact`/`load_artifact` (a single-file adapter with a format tag and identity check), the `validate_inputs`, `validate_dataset`, `split_records` and `evaluation_report` stage helpers, `box_iou`, `preprocess`, and the deterministic in-code sample data in `samples.py`.

#### Intended Use and Limitations

The uses below are the ones the package was built to support; everything else is either out of scope (§Out-of-scope use cases) or prohibited (§Use cases).

###### Primary Intended Uses

Two tasks. **Detection:** input one image (`PIL.Image.Image`, any mode, converted to RGB), a confidence threshold and an NMS threshold; output a list of detections, each an xyxy pixel box, a `label` among the 80 COCO classes and the objectness × class `score`, sorted by score. **Adaptation:** input a list of `{"image", "boxes", "labels"}` records over a caller-chosen class vocabulary; the pipeline re-heads the detector onto that vocabulary, keeps the COCO-pretrained backbone, neck, box and objectness weights, runs a bounded SimOTA fine-tune, scores a held-out split, and exports a reloadable artifact. Envisioned applications are everyday-scene detection where the COCO vocabulary fits, and — more to the point of this row — adapting a small, permissively licensed detector to a narrow domain vocabulary a user can label a few dozen images for: parts on a line, symbols on a form, markers in a field survey. Within DIMER the pipeline is an inference and fine-tuning component and a low-cost baseline for detection work, not a certified detector for any camera, scene or class. YOLOX-S is the small variant; YOLOX-X is a separate DIMER row with its own repository and the same code path at `depth = 1.33`, `width = 1.25`.

###### Primary Intended Users

Intended users are machine-learning engineers, computer-vision developers, and data analysts integrating object detection, or a first detection fine-tune, into research prototypes, internal tooling, or the DIMER workbench. A user is expected to understand that the pretrained vocabulary is the 80 COCO classes and nothing else; that a `score` is a product of two independent sigmoids — a ranking signal within one image, not a calibrated probability on their data; that both thresholds trade recall against spurious boxes and must be tuned per deployment; that the model was trained on COCO photographs, so drawn graphics, documents, aerial, medical and infrared imagery are distribution shifts (the tutorial's drawn football is missed entirely); and that a fine-tune on a few dozen images produces a model fitted to those images, whose held-out score on data from the same generator is not evidence about anything else. Users adapting the model are additionally expected to understand that re-heading discards the COCO classifier — an adapted model answers **only** in the new vocabulary — and that the defaults in this repository (six epochs, learning rate 1e-3, frozen backbone) were measured on this repository's own synthetic dataset and will not automatically transfer. Users who need open-vocabulary prompts, segmentation masks, tracking IDs, batched or video inference, or upstream's TensorRT throughput are expected to know none of that is provided here.

###### Out-of-scope use cases

1. **Capability boundary:** no classes outside COCO's 80 without adaptation, no text prompts, no instance or semantic segmentation, no tracking, no keypoints, no batching or video, no calibrated confidence, no quantisation and no ONNX/TensorRT export. The upstream speed figure (9.8 ms per image on a V100) is not reproduced; this repository measures CPU wall time only. Upstream's mosaic and mixup augmentation, its 300-epoch schedule, its EMA, its learning-rate warmup and its L1 box-refinement term (enabled upstream only for the last 15 epochs) are all outside the bounded fine-tuner.
2. **Input boundary:** `detect` rejects non-PIL images (`TypeError`), sides below `MIN_IMAGE_SIDE = 16` px or above `MAX_IMAGE_SIDE = 4096` px, and thresholds outside `[0, 1]` (`ValueError`, booleans included). One image per call; at most `MAX_DETECTIONS = 8400` boxes can survive, one per anchor point. `finetune` rejects more than `MAX_TRAIN_IMAGES = 200` images, more than `MAX_LABELS_PER_IMAGE = 50` boxes in one image, more than `MAX_CLASSES = 80` classes, more than `MAX_EPOCHS = 20` epochs, boxes outside their image, inverted boxes, and labels outside the declared vocabulary.
3. **Input boundary:** the training data is COCO 2017 train — consumer photographs of everyday scenes. Drawn or rendered graphics (both of this repository's samples), documents and screenshots, aerial, satellite, medical, thermal or underwater imagery, night or heavily degraded frames, and objects outside the 80 classes fall outside what the upstream authors evaluated and what this repository measured; results on them are undefined, not merely degraded.
4. **Decision boundary:** not for autonomous decisions that act on detections — vehicle control, security or surveillance alerts, safety interlocks, medical or industrial inspection — without a human reviewing the detections and a locally measured precision/recall on the deployment's own labelled images at the chosen thresholds. An adapted model is *more* tempting to trust and no more entitled to it: a held-out AP50 of 1.0 on ten synthetic images is not a deployment metric.

#### Factors

###### Groups

This pipeline is human-centric in one respect: `person` is COCO class 0, so the pretrained model localises people in any image, and its recall and score for people vary with the population — COCO's known skews toward North American and European consumer photography, and the object-detection literature's documented disparities in person detection by skin tone, body size, age, clothing (including religious and cultural dress), mobility aids and lighting apply to any COCO-trained detector and were not audited by this repository or, to our knowledge, for this checkpoint. Neither the upstream authors nor this repository evaluated per-group performance; the fairness of a person-detection deployment is unknown, not known to be equal. Objects also vary by region: vehicle types, furniture, foods and signage outside COCO's collection geography are the classes whose recall is unknown. Adaptation does not resolve this and can concentrate it: a fine-tune inherits the frozen backbone's features wholesale, so whatever the backbone represents poorly stays poorly represented, and the adapted model's per-group behaviour is bounded by a training set the user assembled and this repository never saw. The operator who detects people, or who adapts the model to anything correlated with people, is responsible for a per-group audit on their own imagery before relying on the output.

###### Instrumentation

The upstream training instrument is the consumer camera behind COCO — daytime, colour, mostly well-exposed photographs at web resolution, with human-drawn boxes following COCO annotation conventions. Inference images arrive from whatever produced them — a phone, a CCTV or dashboard camera, a drone, a rendering engine — and resolution, motion blur, compression, exposure, lens distortion and viewpoint all change the visual evidence. Preprocessing is upstream's letterbox: aspect ratio preserved, the image pasted at the top-left of a 640×640 canvas filled with grey 114, then **BGR** channel order and raw 0–255 float32 with no rescaling and no mean/std normalisation. Two instrumentation details are measurable and recorded. First, channel order is load-bearing: feeding the same letterboxed tensor as RGB instead of BGR changed the tutorial scene's result from six detections to five, lost the bench entirely, took the stop sign from 0.962 to 0.839 and promoted a spurious second clock from 0.309 to 0.441. Second, this repository reproduces the letterbox with Pillow rather than OpenCV so the runtime stays at torch/torchvision/numpy/Pillow; `cv2.INTER_LINEAR` and `PIL.Image.BILINEAR` are not bit-identical in general, but the resize is skipped entirely when the input is already 640×640 — a Pillow bilinear resize to the source size is verified to be the identity — so every sample in this repository is unaffected and only a differently sized user image goes through the differing kernel. Both sample sets are themselves rendering instruments far from any camera: flat colours, hard edges, no lighting, no occlusion, no blur.

###### Environment

Operating environment: Python 3.12 with `torch==2.14.0`, `torchvision==0.29.0`, `numpy==2.5.3`, `pillow==11.3.0`, float32 on CPU; CUDA is used automatically when visible but was not exercised for this card. There is no `transformers`, no `huggingface-hub`, no `opencv`, no `loguru` and no `yolox` distribution in the dependency set — the model code is vendored and the checkpoint arrives over `urllib` from a release asset. Measured 2026-09-15 on the reference machine (Intel Core Ultra 9 275HX, Windows) with the GPU hidden (`CUDA_VISIBLE_DEVICES=-1`) and `HF_HUB_OFFLINE=1`: `verify_snapshot` on the 1-file, 72 MB snapshot 0.08 s; `from_pretrained` 2.64 s; `detect` on the 640×640 drawn scene 0.11 s (first call) / 0.08 s (second); re-heading onto a 3-class vocabulary 0.20 s; a six-epoch fine-tune on 30 images 25.9 s; scoring 10 held-out images 0.80 s; `save_artifact` 0.08 s and `load_artifact` 0.08 s. Cost is dominated by the fixed 640×640 working resolution, not by the caller's pixel count. Data environment: the pretrained model assumes a photograph of an everyday scene containing COCO objects, which the drawn samples only partly satisfy; the fine-tuner assumes labelled images from the user's own domain, of which this repository supplies only a synthetic stand-in. Real cameras, non-COCO objects, degraded frames and empty scenes violate these assumptions to degrees this repository did not measure, and the pipeline reports no signal when they do.

#### Metrics

###### Performance Measures

For single-image detection the pipeline reports no accuracy measure: each detection carries `score`, the product of the objectness sigmoid and the class sigmoid — a ranking signal within one image, not a probability that the box is a real object of that class on the deployment's images. `box_iou(a, b)` is shipped because it is the primitive every detection metric is built from, and `evaluation_report(result, ground_truth_boxes=None)` returns one `box_iou` entry per supplied reference (its best-overlapping detection **of the same label**, that detection's score, and how many same-label detections existed — a reference with none scores 0.0) with the verdict `sample-sanity`, or `not-measurable` naming the labelled set that would be required. For the adaptation path the pipeline does measure: `average_precision` implements COCO-style matching — per class, detections in descending score order each claim the highest-IoU unclaimed reference above the threshold — with 101-point interpolated precision, averaged over classes with at least one reference and over the ten IoU thresholds 0.50…0.95, exposed as `ap` (AP@[.50:.95]), `ap50` and `ap75`; `evaluate` applies COCO's 100-detections-per-image cap and the evaluation thresholds before scoring. It is a small faithful implementation, **not** `pycocotools`: no area ranges, no crowd handling, no official matching, so its numbers are not comparable to published COCO results. Measured on the repository's own synthetic sign dataset (40 images, 82 boxes; 30 train / 10 held out), held-out AP@[.50:.95] moved **0.2083 → 0.8110** and AP50 **0.2222 → 1.0000** across a six-epoch fine-tune, with per-class AP50 going from 0.0 / 0.0 / 0.667 to 1.0 / 1.0 / 1.0 for `stop-sign` / `yield-sign` / `speed-limit-sign`. The pre-adaptation baseline is not zero because only the classification branch is re-initialised: the COCO-trained box and objectness heads already localise a sign-shaped object. Upstream's reported COCO numbers for YOLOX-S at 640 (mAP 40.5 on both val and test-dev, 9.8 ms on a V100, 9.0 M parameters, 26.8 GFLOPs) are upstream-reported and this pipeline neither reproduces nor claims them.

###### Decision thresholds

Two thresholds are applied, both caller-owned request parameters rather than hidden constants, and the package names upstream's two pairs rather than averaging them into one house default. The **demo pair**, `DETECTION_THRESHOLD = 0.3` and `NMS_THRESHOLD = 0.3`, is what upstream's `tools/demo.py` passes and is meant for looking at results; a prediction survives when objectness × class probability reaches the confidence threshold and then wins per-class NMS. The **evaluation pair**, `EVAL_DETECTION_THRESHOLD = 0.01` and `EVAL_NMS_THRESHOLD = 0.65`, is upstream's `Exp.test_conf` / `Exp.nmsthre` and is what `evaluate` uses, because average precision rewards recall and scoring at the demo thresholds understates it. Neither pair was tuned by this repository and neither is calibrated for any deployment. The measured sensitivity on the tutorial scene is mild for real objects and informative for degenerate ones: 6 detections at the demo pair and 7 at the evaluation pair; a blank white image yields **0 detections at both**; uniform noise yields 0 at the demo pair and exactly 1 (`bear`, 0.073) at the evaluation pair. A deployment owns tuning: lower the confidence threshold when a missed object costs more than a spurious box, raise it when a false detection triggers downstream action, and re-tune whenever the camera, scene or class mix changes. The fine-tuning hyperparameters are decision thresholds of a different kind and were chosen by measurement, recorded in `docs/release-verification.md`.

###### Approaches to uncertainty and variability

Every random choice in this repository is seeded and the seeds are public: sample generation (`sign_dataset(seed=)`), the train/held-out split (`split_records(seed=)`), the re-headed classification layers (`from_pretrained(seed=)`, which saves and restores the global RNG state so it cannot perturb a caller's stream) and the training shuffle (`finetune(seed=)`). That seeding is load-bearing rather than cosmetic: before it was added, the re-headed layers were initialised from whatever the ambient global RNG held, and the pre-adaptation baseline moved between 0.2121 and 0.4455 AP50 across otherwise identical runs — an irreproducible baseline would have made the before/after comparison meaningless. With seeding, two identical configurations in the measured grid agreed to every digit, including per-image detection counts. What is **not** estimated is dispersion: the reported AP figures are single runs on one 10-image held-out split with one seed, with no confidence interval, no repeated-seed spread and no cross-validation, and a 10-image split cannot support one. Run-to-run variability also comes from floating-point kernel selection across CPU builds and accelerators, so a fixed input on fixed hardware is repeatable but not guaranteed bitwise-identical across machines. The `score` is a product of sigmoids, not a calibrated confidence: on the drawn scene the four found objects scored 0.545–0.962 with `box_iou` 0.914–0.959, while the football scored below the threshold for `sports ball` at every setting and surfaced as `kite` 0.369 instead — observations that illustrate uncalibration, not a calibration curve. A caller who needs calibrated confidences must fit a calibration map on their own labelled images; a caller who needs an uncertainty estimate must supply enough labelled images to compute one.

#### Ethical considerations and biases

No external ethics board, red-team, or population-specific clearance reviewed this repository or, to our knowledge, the upstream checkpoint; nothing below should be read as implying one.

###### Data

The upstream README states that the standard YOLOX models are trained on COCO; the COCO paper describes images collected from Flickr under Creative Commons licences and annotated by crowd workers. COCO contains photographs of identifiable people, licence plates, house numbers and personal environments, so personal data in the training corpus is present by construction and was not audited here; the `person` class exists precisely to localise people. This repository distributes code, tests, and documentation; it does not distribute the 72,089,125-byte `yolox_s.pth`, which is staged locally under `weights/yolox-s/` and git-ignored, and it ships **no photographs at all** — both the COCO demonstration scene and the 40-image adaptation dataset are drawn in code with Pillow and carry no personal data of any kind. The adaptation dataset is a deliberate stand-in, not a real corpus: a user who adapts this model supplies their own images, and the operator must audit those for personal, proprietary, or otherwise restricted content. The pipeline performs no such check, will localise a person in a private photograph as readily as a chair, and will happily fine-tune on data it has no right to.

###### Human Life

This pipeline is not intended for decisions in health, safety, criminal justice, employment, credit, or housing, and it has not been validated or certified for any of them by this repository, the upstream authors, or any regulator. Foreseeable but unintended sensitive uses — pedestrian detection for vehicle control, person detection for surveillance, crowd counting for policing, weapon-adjacent object detection for security screening, PPE or hazard detection for safety interlocks — would be admissible only with human review of the detections, a locally measured precision/recall on the deployment's own labelled imagery stratified by the groups named above, a documented threshold and re-validation policy, and whatever regulatory clearance the domain requires. The adaptation capability lowers the effort of building a bespoke detector for a sensitive category; that it is easy does not make it admissible, and a model fine-tuned in a tutorial-sized run is the least qualified to carry such a decision.

###### Mitigations

- **Supply-chain integrity:** `MODEL_REVISION` is an immutable release tag and the checkpoint is pinned by SHA-256. `stage_missing_files` refuses a manifest whose `modelId`/`revision` differ from the package constants and downloads only manifest-listed files from that tag's release assets, and only with `allow_download=True`; `verify_snapshot` then checks byte size and SHA-256 **before** anything unpickles the file; `from_pretrained` calls `torch.load(..., weights_only=True)`, which refuses arbitrary globals, and never `torch.hub.load_state_dict_from_url` (upstream's own loader, which downloads with no digest check, is deliberately not vendored). Artifacts are checked the same way: `load_artifact` refuses a foreign format tag or a mismatched pinned identity before building a model. Tests flip a manifest digest, truncate a file, forge a manifest identity, and tamper with an artifact's format tag, and assert each is refused; the import-boundary tests assert that a missing or tampered snapshot is refused before `torch` is imported at all.
- **Vendored-code integrity:** the eight upstream modules are pinned to a 40-hex commit with per-file SHA-256 in `docs/UPSTREAM.md`; `tools/vendor_upstream.py --check` re-fetches upstream and fails on any divergence, and runs in CI; unit tests assert the three declared edits are each applied exactly once, that no vendored module imports anything outside the pinned runtime, and that the vendored files are excluded from `ruff` so a lint autofix cannot silently fork them.
- **Input integrity:** `validate_inputs` and `validate_dataset` apply exactly the checks `detect` and `finetune` apply (each routes through one shared checker) and return machine-readable manifests recording schema, ceilings, observations and verdict; `validate_dataset` reports a class with no boxes as a finding rather than failing, because that dataset is trainable but its head outputs will not be.
- **Reproducibility:** exact `==` pins; every stochastic step seeded (see §Approaches to uncertainty and variability); every result carries `model_id`, `model_revision` and the request that produced it.
- **Refusals:** no batching, no download without the explicit flag, no thresholds hidden inside the runner, no unqualified `torch.load`, no archive extraction, no remote code execution, and no attempt to guess whether an image contains objects.
- No statistical mitigation (class balancing, resampling) is applied during fine-tuning: the bounded loop trains on the records it is given, in shuffled order, and reports the per-class box counts so an imbalance is at least visible.

###### Risks and harms

- **Misses are silent:** the drawn football is never proposed as a `sports ball` at any threshold; the model offers `kite` 0.369 and a second `clock` 0.309 on that box instead. No field of the output flags a miss, and the downstream consumer bears its cost. An earlier probe was sharper still: a plain white disc with two hands was not read as a `clock` at all, and drawing it that way made the *ball* become the clock — which is why the sample's clock face carries numerals.
- **Mislabelling within the closed vocabulary:** anything outside the 80 classes that resembles one is labelled as it; a system that acts on labels inherits the error.
- **Adaptation creates false competence:** an adapted model answers only in its new vocabulary and answers *confidently* — the tutorial's fine-tuned model scores 0.887–0.917 on unseen synthetic images. Those numbers come from a six-epoch fit to 30 drawn images and say nothing about photographs. A user who ships such a model because its held-out AP50 reached 1.0 has been misled by an easy split, not by the pipeline.
- **Catastrophic fine-tuning:** unfreezing the backbone at the tutorial learning rate was measured to collapse the model to AP 0.0 — a full fine-tune on too little data destroys the pretrained features it depends on. The default freezes the backbone; a user who changes that without lowering the learning rate should expect the same collapse.
- **Person detection and surveillance:** `person` is a first-class output; the pipeline makes people in any image locatable and countable with no consent or purpose check, and its per-group recall is unaudited.
- **Automation bias:** tight boxes with high scores invite trust that a product of two sigmoids has not earned.
- **Bias amplification:** any scene, object or population COCO under-represents is reproduced as uneven recall, undetected because no per-group evaluation exists; a frozen-backbone fine-tune inherits it wholesale.
- **Resource use:** small model (72 MB, ~0.1 s per image and ~26 s for a bounded fine-tune on the reference CPU); a video stream or an unbounded training loop can still saturate a shared host, which is why the ceilings exist.

###### Use cases

Prohibited even where the model would work: detecting people in order to surveil, track, profile, or score them, or to enable unlawful discrimination in employment, housing, credit, insurance, education, healthcare access or law enforcement; adapting the detector to recognise individuals, protected characteristics, or proxies for them; processing or training on imagery the operator has no right to use, or in breach of consent, privacy or data-protection obligations; deceptive uses that present detections as verified facts or as evidence; autonomous physical control or safety interlocks based on unreviewed detections; and any use that violates the upstream Apache-2.0 licence terms or the DIMER deployment terms. Autonomous high-consequence actions triggered by unreviewed detections are prohibited by the intended-use contract above.

## Input/output contract

- `YoloxDetectionPipeline.from_pretrained(device=None, weights_dir=None, allow_download=False, class_names=None, seed=0)` — stages missing manifest files (only with `allow_download=True`), verifies digests, loads. With `class_names` the classification branch is rebuilt for that vocabulary (seeded) and the six `head.cls_preds.*` tensors are reported in `reinitialised`; without it the 80 COCO classes load `strict=True`. `device` defaults to `cuda:0` when visible, else `cpu`.
- `detect(image, *, threshold=0.3, nms_threshold=0.3) -> dict` with keys `detections` (list of `{"box": [x0, y0, x1, y1], "label", "score"}` in input-pixel coordinates, sorted by descending score, at most 8400 entries), `threshold`, `nms_threshold`, `width`, `height`, `class_names`, `adapted`, `model_id`, `model_revision`. `detect_many(images, ...)` is one `detect` per image at the evaluation thresholds.
- `finetune(records, *, epochs=6, batch_size=2, learning_rate=1e-3, seed=0, freeze_backbone=True, progress=None) -> dict` — validates, trains with upstream's SimOTA loss, returns the dataset manifest, per-epoch losses, the optimiser description, trainable/total parameter counts and the request. Mutates the pipeline in place and leaves it in eval mode.
- `evaluate(records, *, threshold=0.01, nms_threshold=0.65, iou_thresholds=COCO_IOU_THRESHOLDS, max_detections=100) -> dict` — `ap`, `ap50`, `ap75`, `per_class_ap50`, `scored_classes`, the request, and `detections_before_cap`.
- `save_artifact(path, *, notes=None) -> dict` and `YoloxDetectionPipeline.load_artifact(path, *, device=None)` — one `.pt` holding the state dict plus format tag, pinned identity, class vocabulary and architecture constants; no archive, and reload uses `weights_only=True`.
- Ceilings and constants: `MIN_IMAGE_SIDE = 16`, `MAX_IMAGE_SIDE = 4096`, `MAX_DETECTIONS = 8400`, `MAX_LABELS_PER_IMAGE = 50`, `MAX_TRAIN_IMAGES = 200`, `MAX_EPOCHS = 20`, `MAX_CLASSES = 80`, `MAX_EVAL_DETECTIONS = 100`, `LABELS` (80 COCO classes in upstream order), `INPUT_SIZE = (640, 640)`, `PAD_VALUE = 114`, `INPUT_SCHEMA`, `TRAIN_SCHEMA`.
- Helpers: `box_iou(a, b)`; `preprocess(image) -> (CHW float32 BGR array, ratio)`; `validate_image`, `validate_inputs`, `validate_dataset`, `split_records`, `average_precision`, `evaluation_report`, `verify_snapshot`, `stage_missing_files`; deterministic sample data in `samples.py` (`tutorial_scene`, `blank_scene`, `noise_scene`, `sign_dataset`, `SIGN_CLASSES`).

## Runtime

- Pins: `torch==2.14.0`, `torchvision==0.29.0`, `numpy==2.5.3`, `pillow==11.3.0`; Python 3.12. No `transformers`, `huggingface-hub`, `opencv`, `loguru` or `yolox` distribution.
- Precision: float32. Preprocessing: letterbox to 640×640 with aspect ratio preserved and a `114` grey pad, BGR channel order, raw 0–255 values, no rescaling and no mean/std normalisation (upstream `ValTransform(legacy=False)` semantics, reproduced with Pillow).
- Measured 2026-09-15 in the Windows venv (`torch 2.14.0+cu130`) with `CUDA_VISIBLE_DEVICES=-1` and `HF_HUB_OFFLINE=1`, device `cpu`: `verify_snapshot` 0.08 s (1 file, 72 MB); `from_pretrained` 2.64 s; 8,968,255 parameters. `detect` on the 640×640 drawn scene at 0.3/0.3 → 6 detections in 0.11 s (0.08 s on the second call): `stop sign` 0.962, `traffic light` 0.863, `clock` 0.855, `bench` 0.545, `kite` 0.369, `clock` 0.309. `box_iou` against the drawn references: stop sign 0.946, traffic light 0.914, clock 0.946, bench 0.959, **sports ball 0.000** (no `sports ball` detection at any threshold; the football's box surfaces as `kite` and a second `clock`). 7 detections at the evaluation thresholds 0.01/0.65. Blank white image → 0 detections at both threshold pairs; uniform noise (NumPy default generator, seed 0) → 0 at the demo pair and 1 (`bear` 0.073) at the evaluation pair. Channel-order probe: the same tensor fed as RGB → 5 detections, bench lost, stop sign 0.839, second clock 0.441.
- Adaptation measured in the same run: `sign_dataset(40, seed=0)` → 40 images, 82 boxes (`stop-sign` 21, `yield-sign` 34, `speed-limit-sign` 27), no findings; `split_records(holdout=0.25, seed=0)` → 30 train / 10 held out; re-heading reinitialised exactly the six `head.cls_preds.{0,1,2}.{weight,bias}` tensors in 0.20 s; baseline on the held-out split AP 0.2083 / AP50 0.2222 (per class 0.0 / 0.0 / 0.667); `finetune(epochs=6, batch_size=2, learning_rate=1e-3, seed=0, freeze_backbone=True)` 25.9 s over 15 steps per epoch, training 1,891,096 of 8,938,456 parameters, mean `total_loss` 6.288 → 1.662 and `num_fg` stable at 8.2–8.8; adapted AP **0.8110** / AP50 **1.0000** (per class 1.0 / 1.0 / 1.0) in 0.80 s; three images from an unseen seed → all five objects detected with the correct label at 0.887–0.917 and same-label `box_iou` 0.886–0.949; `save_artifact` 35,998,819 bytes over 462 tensors in 0.08 s; `load_artifact` in a fresh object reproduced AP 0.8110 / AP50 1.0000 exactly; an artifact with a tampered format tag was refused.
